# Terra Analog — Frontend UI/UX Specification

**Status:** Approved visual concept for Phase 1 implementation. Review by the Frontend & Data Lead is a Phase 1 readiness criterion (see [frontend/README.md](../frontend/README.md#phase-1-readiness)).

**Authority:** [docs/api-contract.md](api-contract.md) is the technical source of truth for backend/frontend communication. [PROJECT-CONTEXT.md](../PROJECT-CONTEXT.md) is the source of truth for scope. If this specification differs from either, **report the conflict**; do not silently change the API contract, the backend or this specification. Known gaps are listed in [section 16](#16-contract-alignment-and-open-items).

Text marked **(proposal)** is a suggestion that is not part of the approved concept.

## 1. Product concept

Terra Analog is a scientific terrain comparison web application. The user uploads an Earth elevation GeoTIFF. The backend analyzes it and compares its terrain geometry with a prepared Mars reference, initially Gale Crater.

The frontend receives:

- an Earth terrain preview image generated by the backend,
- a prepared Mars reference preview image,
- JSON with similarity scores, slope distribution chart data, metadata and warnings.

The frontend must **not** calculate elevation, slope, roughness, relief or similarity. It only displays what the backend returns.

## 2. Visual design system

Approved style: **dark Mars-inspired scientific dashboard**.

- Nearly black background, dark charcoal panels, Mars-orange primary accents, white and light-gray text.
- Subtle borders and restrained shadows.
- Clean, modern scientific typography.
- Large terrain visualizations are the primary visual focus.
- Professional, responsive dashboard layout.

Suggested initial design tokens (visual guidelines; the frontend developer may refine them consistently):

| Token | Value |
| --- | --- |
| Background | `#080B10` |
| Panel | `#151A22` |
| Secondary panel | `#202734` |
| Primary accent | `#E87932` |
| Hover accent | `#FF9D57` |
| Primary text | `#F3F5F8` |
| Secondary text | `#A3ADBB` |
| Error | `#EF5350` |

Avoid excessive animations, decorative planets, unnecessary 3D effects and gaming-style graphics.

**(proposal)** Accessibility note: light text on the `#E87932` accent has a contrast ratio of roughly 2.7:1, which is low for button labels. Dark text (`#080B10`) on that accent is roughly 6.8:1. Check contrast when refining tokens.

## 3. Page structure

The application is **one continuous page**. There are no separate routes for upload and results. Do not add React Router or separate React pages unless the human developers approve a genuine technical need.

| # | Section | Visible |
| --- | --- | --- |
| 1 | Header | Always |
| 2 | Hero / project introduction | Always |
| 3 | Earth GeoTIFF upload | Always |
| 4 | Mars reference information | Always |
| 5 | Processing state | While an analysis is running or has failed |
| 6 | Comparison results | After a successful analysis |
| 7 | Detailed terrain charts | After a successful analysis |
| 8 | Scientific interpretation / limitations | After a successful analysis |
| 9 | Footer | Always |

Sections 5–8 appear only when their data or application state exists.

## 4. Header

- Left: **TERRA ANALOG**.
- Right: **Home**, **About**, and the **EN / RU** language toggle.

| Control | Behavior |
| --- | --- |
| Home | Returns to the top of the page. It must not clear the current analysis or discard an uploaded file unexpectedly. |
| About | Opens a modal explaining the project's purpose, NASA data sources, terrain similarity and scientific limitations. |
| EN / RU | Switches all user-visible interface text between English and Russian, without reloading the page or erasing analysis results. |

## 5. Upload section

Heading: **Compare Earth's Terrain with Mars**

Subtitle: "Upload an Earth elevation model to explore similarities with the Martian landscape."

Components:

- Drag-and-drop file upload zone.
- **Browse File** button.
- Selected filename.
- Supported format information: `.tif`, `.tiff`.
- Fixed Mars reference card.
- **Analyze Terrain** button.

The client-side extension check is preliminary. Backend validation is authoritative, and backend errors such as `INVALID_DEM` are shown to the user. Upload size limits are unresolved, so the frontend does not enforce or state any.

The MVP has **one** reference, **Gale Crater — Mars**, with identifier `mars-gale`. Do not implement a reference dropdown or a Change Reference button.

## 6. Buttons and actions

| Action | Behavior |
| --- | --- |
| Browse File | Opens the native file picker for a candidate Earth GeoTIFF. |
| Analyze Terrain | Enabled only after a file is selected. Sends `multipart/form-data` to `POST /analyze` with `file` and `reference_id=mars-gale`. Shows the processing state, and on success shows the results. |
| New Analysis | Clears the previous results and selected file and returns to the upload state. Keeps the chosen language. |
| Zoom In (+) | Increases the displayed map image scale. |
| Zoom Out (−) | Reduces the displayed map image scale. |
| Reset View | Restores a map to its initial fit and position. |
| About | Opens the informational modal. |
| Close | Closes the About modal. |
| EN / RU | Changes the language without losing state. |
| Export Report | **Optional stretch feature.** Do not render a functional-looking button unless export is implemented. Do not invent a backend export endpoint. If implemented, agree the report format and contents first. |

**Out of scope:** Change Reference, Swap DEMs, Layer Selector, multiple planetary references, a 3D globe, and AI-generated scientific interpretation.

## 7. Processing state

After **Analyze Terrain** is pressed:

- Show a loading indicator and the text "Analyzing terrain data..." (or its Russian equivalent).
- Disable duplicate submissions.
- Preserve the selected filename.
- On failure, show a meaningful error message and allow the user to retry.
- Do not show invented progress percentages.

The frontend must not substitute mock data when the backend fails or is unavailable. If the backend is unreachable, show a clear message saying so.

## 8. Results dashboard

Results appear on the **same page** after a successful analysis.

**Desktop layout**

- Primary content area: two large terrain images, **Mars on the left, Earth on the right**.
- Summary sidebar: Overall Terrain Similarity, the Relative Relief, Slope Distribution and Surface Roughness scores, and reference metadata and warnings where appropriate.
- Below: Similarity Breakdown chart, Slope Distribution comparison chart, scientific limitations and data provenance, and the New Analysis action.

**Smaller screens**

- Stack the maps vertically, with the score summary beneath them.
- Keep charts readable and responsive.
- Do not force horizontal page scrolling.

## 9. Terrain maps

| Map | Source |
| --- | --- |
| Mars | The prepared PNG at `reference.preview_url`. Reference name: Gale Crater (`reference.name`). Must not be a hardcoded stock image. |
| Earth | The visualization at `earth_preview_url`, generated from the uploaded GeoTIFF. It must reflect the actually analyzed dataset. |

Both maps support zoom in, zoom out, pan/drag while zoomed, and reset view. These interactions only transform the rendered PNG. They do not recalculate geographic data, and zoom is a display feature, not a measurement tool.

- Initial fit and zoom limits are consistent for both maps, and the image never overflows its container.
- Do not add an Earth OpenStreetMap basemap beneath Mars.
- Do not imply that the two maps show identical distances unless that is scientifically verified.
- Show a scale bar only when valid scale metadata is available. The current API contract provides none, so there is no scale bar in the MVP, and no fictional distance labels.

## 10. Similarity summary

- The overall similarity (`total_similarity`) is displayed prominently.
- Three secondary cards: Relative Relief, Slope Distribution, Surface Roughness (`scores.*`).
- The backend returns values from 0 to 1. The frontend displays them as **percentages with one decimal place**: `0.874` → `87.4%`. This rounding is display formatting only.
- Do not invent score values.
- If `is_mock` is `true`, show a clearly visible **DEMO / MOCK DATA** indicator. Mock data must never be presented as real scientific results, and real results must never be presented as simulated.
- **(proposal)** If a required score is missing, non-numeric or outside 0–1, treat the response as invalid and show an error rather than clamping or substituting a value.

## 11. Charts

The MVP has exactly two chart types. Use an established React charting library, such as Recharts, chosen during implementation.

**Chart 1: Similarity Breakdown.** A bar chart of Relative Relief, Slope Distribution and Surface Roughness similarity from the `scores` object, on a percentage scale from 0 to 100.

**Chart 2: Slope Distribution.** Compares Earth and Mars using only backend data:

- shared `bin_edges`,
- `earth` fractions per bin,
- `mars` fractions per bin,
- the `unit` provided by the backend.

Use grouped bars or two clearly differentiated series. Label both planets and the units. Never generate arbitrary values.

**(proposal)** Label bins from `bin_edges` (for example "0–5"), show the backend `unit`, and show the fractions as a share of valid cells. Show known unit values such as `degrees` through the translation dictionary and fall back to the backend string.

Do not add relief or roughness graphs until the backend contract provides the numerical datasets for them.

## 12. Scientific information

A concise section that states:

- Mars data originates from NASA MOLA.
- Earth data is uploaded by the user.
- Similarity concerns terrain geometry only.
- Similarity does not establish habitability, safety or suitability for construction.
- Results depend on DEM resolution, study area and methodology.

Display backend `warnings` without hiding them. Do not invent scientific conclusions beyond returned data and approved documentation. The same statements apply in the About modal.

## 13. Localization

English and Russian are both required.

- Keep all interface labels and messages in a centralized translation system, in `frontend/src/i18n/`. Do not scatter English strings across components.
- A small local dictionary is acceptable. Do not require an external translation API.
- Buttons, section headings, validation messages, loading text and interpretation labels are all translatable.

Backend-provided `warnings[].message` and `error.message` are currently English only. See [section 16](#16-contract-alignment-and-open-items).

## 15. API integration

The [API contract](api-contract.md) is the source of truth. Required endpoints: `GET /health`, `GET /references`, `POST /analyze`.

| Endpoint | Frontend use |
| --- | --- |
| `GET /health` | Check that the backend is reachable. |
| `GET /references` | Load reference metadata. Display only the approved Gale reference (`id` `mars-gale`). No selector. |
| `POST /analyze` | Upload the Earth file with `FormData`. |

Response fields the UI uses:

| Field | Used for |
| --- | --- |
| `status` | Success/error handling |
| `is_mock` | DEMO / MOCK DATA indicator |
| `reference.id`, `reference.name`, `reference.dataset`, `reference.effective_resolution_m` | Reference card and metadata |
| `reference.preview_url` | Mars map |
| `earth_preview_url` | Earth map |
| `total_similarity` | Overall similarity |
| `scores.relative_relief`, `scores.slope_distribution`, `scores.surface_roughness` | Score cards and Similarity Breakdown chart |
| `charts.slope_distribution.unit`, `.bin_edges`, `.earth`, `.mars` | Slope Distribution chart |
| `warnings[].code`, `warnings[].message` | Warnings panel |

Integration rules:

- The Earth preview may be an inline `data:` URL. The Mars preview may be a backend-relative URL.
- Resolve backend-relative URLs against a configured backend API base URL. Never prefix or modify `data:` URLs.
- Make the API base URL configurable through Vite environment settings (**proposal:** `VITE_API_BASE_URL`). Do not hardcode localhost URLs in UI components.
- `reference.effective_resolution_m` may be `null` until verified. Handle `null` without inventing a value.
- Do not assume fields that are missing from the approved contract, and do not silently rename or change API fields in frontend code.
- Send proposed API changes to the backend developer for approval.
- Show useful error messages when the backend is unavailable.

## 16. Contract alignment and open items

**Differences between this specification and the API contract**

1. The contract marks `mars-gale` as a *proposed* identifier. This specification treats it as fixed. Confirm it with the backend and data owners. If it changes, both documents change together.
2. The contract describes `GET /references` as the list the user can select from, and says Gusev Crater appears once prepared. The MVP UI shows only `mars-gale`. Showing more references later needs a human-approved change.
3. Backend `warnings[].message` and `error.message` are English only, so Russian mode would show English backend text. **(proposal)** Translate known warning and error `code` values in the dictionary and fall back to the backend message. The code lists are not yet defined.
4. The contract has no scale metadata, so no scale bar is shown.
5. The contract leaves score display and numeric precision open. This specification decides display only: percentages with one decimal place. The backend sends unrounded 0–1 values.
6. Upload limits, error codes and warning codes are unresolved in the contract. The frontend shows the backend message and a generic fallback.

**Open decisions for the human developers**

- Whether the frontend uses JSX or TypeScript (must be documented before implementation).
- How the Phase 1 mock-supported UI loads the fixtures in `data/examples/`, which sit outside `frontend/`. Copies could drift from the contract.
- Whether the upload section stays visible above results, and whether pressing Analyze again replaces results or requires New Analysis.
- Map zoom limits, and whether the two maps zoom independently or together.
- The default language, and whether the choice is remembered.
- Footer content, additional hero copy, and who writes and reviews the Russian text.
- How the `GET /health` result is presented.
- Whether Export Report is attempted at all.
